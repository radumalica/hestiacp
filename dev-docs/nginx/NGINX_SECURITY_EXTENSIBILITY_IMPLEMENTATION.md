# Nginx Security & Extensibility — Implementation (Sprint 8)

## 1. Existing architecture discovered

Hestia renders a per-domain Nginx config with pure `sed -e "s|%var%|value|g"`
text substitution (`add_web_config()` in `func/domain.sh`) over a template
file selected by app type (`func/rebuild.sh`'s `rebuild_web_domain_conf()`).
No `eval`, no shell code execution from template content — the injection
surface is bounded to whatever values get substituted for `%var%`
placeholders.

Templates live in two places:
- `install/deb/templates/web/nginx/` — the repo copy, shipped in the
  package.
- `$HESTIA/data/templates/web/nginx/` (`$WEBTPL`) — the runtime,
  admin-editable copy, populated from the repo copy at install time and
  re-synced by `bin/v-update-web-templates` (a blunt `cp -rf` of the whole
  `nginx/` tree).

Every shipped template already ends with a wildcard `include` for a
per-domain, admin-owned config file:

```
include %home%/%user%/conf/web/%domain%/nginx.conf_*;
```

Only the single file matching `$WEB_SYSTEM.conf` (rendered from the
template) is ever regenerated by a domain rebuild. Every other file in
that directory — including anything matching a wildcard include already
in the template (`nginx.conf_*`, `nginx.fastcgi_cache.conf*`,
`nginx.forcessl.conf*`, `nginx.hsts.conf*`) — is never touched. This is
Hestia's existing, already-safe extension mechanism, and it is what this
sprint builds on rather than replaces.

Globally, `install/deb/nginx/nginx.conf` (unmodified by this sprint) ends
its `http{}` block with:

```
include /etc/nginx/conf.d/*.conf;
include /etc/nginx/conf.d/domains/*.conf;
```

— the safe place to add new *global* (http-context-only) directives
without editing the master file. Individual files under
`install/deb/nginx/*.conf` are deployed there one at a time via `cp -f`
in the installer scripts (confirmed pattern: `status.conf`,
`0rtt-anti-replay.conf`, `agents.conf`, `cloudflare.inc`, etc.).

No ModSecurity module, OWASP CRS, or WAF integration exists anywhere in
this repository's installer, on either the panel's own bundled Nginx or
the system Nginx used for hosted domains (confirmed via full-repo grep).

## 2. Problem / limitations of the prior state

WordPress hosting used one flat template (`wordpress.tpl`/`.stpl`) with a
single hard-coded PHP-execution deny rule scoped only to
`uploads|files`. There was no way to add a security feature (headers, rate
limiting, a WAF) to a domain without either editing the shared template
(affecting every domain using it) or hand-writing a full custom template.
Every additional "profile" would have meant another complete template
file — the ~90 app-specific templates under
`install/deb/templates/web/nginx/php-fpm/` are already evidence of that
pattern not scaling.

## 3. Architecture implemented

**Composition, not proliferation.** A domain's final config is:

```
base template (wordpress.tpl/.stpl)
  + baseline WordPress security profile (always on, in the template)
  + optional feature snippets (opt-in, via a new wildcard include)
  + existing generic admin config (nginx.conf_*, unchanged)
```

The only structural change to the template mechanism is one new wildcard
include point, added to `wordpress.tpl`/`.stpl` only:

```
include %home%/%user%/conf/web/%domain%/nginx.features.conf_*;
include %home%/%user%/conf/web/%domain%/nginx.conf_*;
```

Enabling a feature for a domain = placing a file at
`nginx.features.conf_<name>` (or `nginx.features.ssl.conf_<name>` for the
SSL vhost) in that domain's own conf directory. Nginx's own wildcard
`include` does the composition; no new Hestia bash/PHP logic was needed.
The include matches zero files — and therefore changes nothing — for any
domain that doesn't use it.

A library of reference snippets ships at
`install/deb/templates/web/nginx/snippets/` (inside `nginx/` specifically
so `v-update-web-templates`'s existing `cp -rf .../nginx "$WEBTPL/"` sweeps
it automatically, with no new sync-script special-casing):

- `security-headers.conf` — opt-in, low-risk response headers.
- `fastcgi-cache-example.conf` — references the existing global
  `microcache` FastCGI cache zone.
- `rate-limit-example.conf` — references the new global rate-limit zone
  (below).
- `modsecurity-example.conf` — fully commented-out extension-point
  documentation (module not installed; see §9).

These files are **not** processed by `add_web_config()`'s sed pipeline —
they are raw Nginx config, `include`d directly, and must never contain a
Hestia `%var%` placeholder (verified by the test suite, §7).

### Rate limiting

`limit_req_zone` can only be declared in Nginx's `http{}` context, never
inside a per-domain `server{}` block. The zone declaration therefore
lives in a new global file, `install/deb/nginx/hestia-rate-limit.conf`,
deployed to `/etc/nginx/conf.d/` the same way `agents.conf` is (new `cp
-f` line in both `install/hst-install-ubuntu.sh` and
`install/hst-install-debian.sh`, plus a backfill line for existing
installs — §8). Declaring the zone has no effect on any domain until a
domain's own `nginx.features.conf_*` snippet references it. No
"industry standard" rate/burst value is asserted — the shipped zone uses
a documented, conservative default (`10r/s`), and every consuming
location chooses its own `burst`.

## 4. Configuration ownership

| Path | Owner | Regenerated by |
|---|---|---|
| `install/deb/templates/web/nginx/php-fpm/wordpress.tpl`/`.stpl` | Hestia (this repo) | `v-update-web-templates` / package upgrade |
| `$HESTIA/data/templates/web/nginx/...` | Runtime copy of the above | same |
| `~/conf/web/<domain>/<web_system>.conf` | Generated per-domain | `v-rebuild-web-domain` / `add_web_config()` |
| `~/conf/web/<domain>/nginx.conf_*` | Administrator | **never** regenerated |
| `~/conf/web/<domain>/nginx.features.conf_*` (new) | Administrator | **never** regenerated |
| `install/deb/nginx/hestia-rate-limit.conf` → `/etc/nginx/conf.d/` | Hestia (this repo) | installer / explicit upgrade backfill |

No file an administrator controls is ever overwritten by this
architecture.

## 5. WordPress security profile

Two baseline rules, always on for `wordpress.tpl`/`.stpl`, both `deny
all; return 404;` — rejected at the Nginx boundary, before PHP-FPM ever
runs; nothing is moved or deleted on disk:

1. **Sensitive files**: `wp-config.php`, `wp-config-sample.php`,
   `readme.html`, `license.txt`, `wp-content/debug.log` — none of these
   are ever legitimately requested over HTTP by WordPress, a plugin, or
   WooCommerce.
2. **PHP execution in writable directories**: `wp-content/uploads/*.php`
   and `wp-content/cache/*.php` — both are directories WordPress or a
   caching plugin can write to, the classic path for a planted/uploaded
   PHP file to be executed. `wp-admin`, `wp-includes`, and
   `wp-content/plugins|themes` are untouched — they legitimately execute
   PHP.

**Correctness note (found and fixed during Sprint 8's own testing, not
by inspection alone):** both blocks must be nested *inside* `location /`,
before the general PHP-execution location — not declared as a
server-level sibling of `location /`. Live testing with a real Nginx
binary showed that a server-level regex location can lose to a *nested*
regex location matching the same URI when both are present (Nginx
resolves the nested one for this case), which would have silently
un-blocked `wp-config.php`. Both templates nest the blocks correctly
(see `wordpress.tpl`/`.stpl`, inside `location /`, before `location ~
[^/]\.php(/|$)`), and the test suite in §7 verifies the actual serving
behavior, not just the config text, to guard against this class of bug
recurring.

## 6. Extension points

| Extension | Mechanism | Status this sprint |
|---|---|---|
| Feature snippets (security headers, rate limiting, cache) | `nginx.features.conf_*` wildcard include | Implemented, 2 reference snippets shipped |
| ModSecurity / OWASP CRS / third-party WAF | Same mechanism (`nginx.features.conf_*`), no runtime toggle | **Documented only** — dependency (module + ruleset) not present in this repo; see §9 |
| Future application profiles | New `<app>.tpl`/`.stpl` template following the same nested-location pattern | Not built; architecture supports it |
| Custom admin snippets | Existing `nginx.conf_*` (unchanged) | Pre-existing, untouched |

## 7. Security model

- **No arbitrary directive injection from untrusted input**: the sed
  substitution pipeline (`func/domain.sh`, `func/rebuild.sh`) was not
  modified. Feature snippets are files an administrator places on disk
  themselves — never generated from domain input.
- **No arbitrary include paths**: the new include (`nginx.features.conf_*`)
  is a fixed, template-baked path pattern under the domain's own
  Hestia-managed conf directory — identical trust boundary to the
  pre-existing `nginx.conf_*` include.
- **No path traversal / command execution surface added**: no new shell
  logic was introduced; the only new bash is two `cp -f` lines in the
  installers and a handful of idempotent lines in the 1.10.0 upgrade
  script, all operating on fixed, repo-controlled source paths.
- **No admin-owned file is ever overwritten** (§4).
- Verified untouched: `web/inc/api/`, API v2, legacy `web/api/`,
  `bin/v-*`, adapter/auth infrastructure — no dependency was found that
  required touching them.

## 8. Upgrade / rebuild behavior

`install/upgrade/versions/1.10.0.sh` sets `UPGRADE_UPDATE_WEB_TEMPLATES`
to `false` (pre-existing, unrelated to this sprint — left as-is rather
than flipped, to avoid an unrelated full template resync for every other
app type bundled into this release). Because of that flag, the normal
`upgrade_rebuild_web_templates()` path will **not** auto-sync the
modified `wordpress.tpl`/`.stpl` or the new `snippets/` directory into
`$HESTIA/data/templates/web/nginx/` for an in-place upgrade through this
version. `1.10.0.sh` therefore backfills the *specific* files this
sprint changed — mirroring the existing "Fix File Manager"
targeted-`cp -f` pattern already in that script — rather than touching
the broader flag:

```
cp -f "$HESTIA"/install/deb/templates/web/nginx/php-fpm/wordpress.tpl "$HESTIA"/data/templates/web/nginx/php-fpm/wordpress.tpl
cp -f "$HESTIA"/install/deb/templates/web/nginx/php-fpm/wordpress.stpl "$HESTIA"/data/templates/web/nginx/php-fpm/wordpress.stpl
cp -f "$HESTIA"/install/deb/templates/web/nginx/snippets/*.conf "$HESTIA"/data/templates/web/nginx/snippets/
```

The new global `install/deb/nginx/hestia-rate-limit.conf` has no
existing sync mechanism at all (it's a new file, not a template), so
`1.10.0.sh` also backfills it directly to `/etc/nginx/conf.d/`.

**Existing WordPress domains are not automatically rebuilt.** Updating
the template library does not retroactively regenerate any live domain's
rendered `.conf` file — this is true of every Hestia template change, not
something new to this sprint. An admin must run `v-rebuild-web-domain`
(or `v-rebuild-web-domains`) for an existing WordPress domain to pick up
the new baseline security profile. This is called out explicitly rather
than forcing a mass rebuild during upgrade, which would be a materially
larger, riskier behavior change than this sprint's scope.

## 9. Testing

`test/nginx/test_wordpress_security_profile.sh` — standalone, no Hestia
install required. Renders `wordpress.tpl`/`.stpl` through the same sed
substitution `add_web_config()` uses, then (when a local `nginx` binary
is available) validates with the real binary:

- `default.tpl`, `hosting.tpl`, `nginx.conf`, and the rendering pipeline
  (`func/domain.sh`, `func/rebuild.sh`) are unmodified (existing behavior
  unchanged when no new profile/feature is enabled).
- No unresolved `%var%` placeholder remains in any rendered template or
  raw snippet.
- `nginx -t` passes on the rendered templates, both with and without
  every shipped feature snippet enabled simultaneously (no
  duplicate/conflicting directives).
- Live behavioral checks over a Unix domain socket (avoids TCP port
  collisions in a shared sandbox): `wp-config.php`,
  `wp-config-sample.php`, `readme.html`, `license.txt`,
  `wp-content/debug.log`, `wp-content/uploads/*.php`,
  `wp-content/cache/*.php` all return 404 without reaching PHP-FPM;
  `index.php`, `wp-admin/admin-ajax.php`, a plugin file, and a theme file
  all reach the PHP-FPM boundary (502, no real backend in the test) —
  i.e. legitimate WordPress PHP execution is preserved.
- The security-headers feature snippet, when enabled, is present on a
  response; absent otherwise.

Result: 23/23 checks pass, confirmed over 3 consecutive runs.
`bash -n` passes on both modified installer scripts and the modified
upgrade script and the test script itself. `git diff --check` is clean.
No PHP files were changed this sprint.

**`nginx -t` availability**: this environment has a real `nginx` binary
(1.18.0), so the suite runs the actual validation rather than skipping
it — including the live-serving behavioral checks, not just syntax.

## 10. Known limitations

- Only `wordpress.tpl`/`.stpl` got the baseline security profile and the
  feature include point. The WordPress *variant* templates
  (`wordpress-disable-xmlrpc`, `wordpress-http3`, `wordpress_mu_subdir`,
  and their `-http3` siblings) were deliberately left untouched this
  sprint — extending them is straightforward (same nested-location
  pattern) but out of scope for "prove the architecture."
- `rate-limit-example.conf` is scoped to the whole domain (server
  context), not to a single PHP-handled path like `/wp-login.php` — doing
  that would require re-deriving the PHP-FPM backend wiring
  (`%backend_lsnr%`) that only Hestia's template renderer resolves, which
  a raw, non-rendered snippet cannot access. Deferred rather than shipped
  half-working.
- No full-page WordPress caching (explicitly out of scope this sprint).
- No CSP or `X-Frame-Options` shipped active — both would need
  per-site tuning to avoid breaking legitimate embeds/asset origins.

## 11. Deferred work

- ModSecurity / OWASP CRS integration: requires installing
  `ngx_http_modsecurity_module` and vendoring or referencing a ruleset —
  an installer/packaging change outside this sprint. Documented as a
  **STOP condition** for this specific sub-feature; `modsecurity-example.conf`
  records the exact steps for a future sprint.
- Per-location rate limiting for WordPress login/admin paths.
- Extending the baseline security profile and feature include point to
  the WordPress variant templates.
- A CSP rollout path (Report-Only mode first, per-site tuning).

## 12. STOP conditions encountered

Only one applies, and it was handled per the task's own explicit
allowance ("document the dependency and stop that part rather than
inventing it"): ModSecurity functionality is confirmed unavailable in
this repository's installer (§1, §9/§11). No other STOP condition was
triggered — the existing template mechanism safely supports the
composable architecture, no generated configuration overwrites
administrator-controlled files, and safe separation between trusted
configuration and domain input was maintained throughout (§7).
